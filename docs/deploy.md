# Развёртывание: что делается руками

Всё, что нельзя сделать из кода. Отмечено, где вмешательство человека
обязательно, а где достаточно один раз нажать кнопку.

## 1. Google Cloud — проект `interpreter-tools`

Разделение проектов сделано осознанно: отдельная квота, отдельные права
и понятный радиус поражения при утечке ключа. Но **деньги общие** —
оба проекта на одном биллинг-аккаунте, кредит и счёт у них один.

| Шаг | Команда или место |
|---|---|
| Включить API | `gcloud services enable texttospeech.googleapis.com --project=interpreter-tools` |
| Сервис-аккаунт | `gcloud iam service-accounts create sync-trainer-tts --project=interpreter-tools` |
| Роль | `roles/serviceusage.serviceUsageConsumer` — см. врезку ниже |
| Ключ | `gcloud iam service-accounts keys create key.json --iam-account=sync-trainer-tts@interpreter-tools.iam.gserviceaccount.com` |
| В переменную | `base64 -i key.json \| tr -d '\n' \| pbcopy` |

**Почему именно `serviceUsageConsumer`.** У Cloud Text-to-Speech нет собственной
IAM-роли: разрешений `texttospeech.*` не существует, а роли `roles/speech.*`
относятся к распознаванию речи и к синтезу отношения не имеют. Нужно ровно право
вызывать включённые в проекте API, то есть `serviceusage.services.use`.

**ADC на Vercel не работает** — там нет ни gcloud, ни постоянной файловой системы.
Ключ сервис-аккаунта обязателен, локальный `gcloud auth application-default login`
годится только для разработки.

### 1а. Gemini — генерация скрипта

Ключ отдельный от Text-to-Speech: там сервис-аккаунт, здесь ключ API.

```bash
gcloud services enable generativelanguage.googleapis.com --project=interpreter-tools
```

Ключ создаётся в Google AI Studio и кладётся в `GEMINI_API_KEY`.

Хорошая новость про бюджет: **для Gemini API spend cap enforcement доступен**,
в отличие от Text-to-Speech. Если будете ставить жёсткий предел в Google —
здесь это работает.

### Бюджет в Google

Spend cap для Text-to-Speech **недоступен**: enforcement поддерживают только
Cloud Run, Cloud Run Functions, Gemini API и Vertex AI. Для озвучки остаются
письма, причём фактические расходы появляются с задержкой в несколько часов.

Поэтому в бюджете (Billing → Budgets & alerts) выбирайте **Alerts only**,
ограничивайте Scope проектом `interpreter-tools`, снимайте обе галочки в Savings
(иначе бюджет считает траты за вычетом кредита и промолчит, пока кредит не
кончится) и обязательно добавьте порог по прогнозу.

Настоящий жёсткий предел — в самом приложении, и он трёхуровневый:
`TTS_BUDGET_USD` за всё время, `TTS_MONTHLY_LIMIT_USD` на месяц по сервису
и личный месячный лимит пользователя. Первое же условие, которое не проходит,
останавливает генерацию с ответом 402.

## 2. Vercel — база данных

**Storage → Create Database → Postgres (Neon)**, привязать к проекту.
Переменные подставятся сами; конфигурация принимает `DATABASE_URI`,
`POSTGRES_URL` и `DATABASE_URL`, так что переименовывать ничего не нужно.

### Резервное копирование — прочитайте, это важно

Вы назвали резервное копирование обязательным, и здесь есть подвох.
Восстановление на момент времени у Neon **на бесплатном плане ограничено
шестью часами**, и включён один ручной снимок. Шесть часов — это не
резервная копия, это отмена последней ошибки.

| План | Окно восстановления | Снимков |
|---|---|---|
| Free | 6 часов | 1 |
| Launch | 1 день | 100 |
| Scale | до 30 дней | 100 |

Что с этим делать:

1. **Минимум — платный план Neon**, чтобы окно было хотя бы сутки.
2. **Не полагаться только на провайдера.** Независимая выгрузка `pg_dump`
   в Vercel Blob по расписанию (Cron Job раз в сутки) переживает и ошибку
   в приложении, и проблемы на стороне Neon, и случайное удаление проекта.
   Задача на это — в `docs/r1-tasks.md`.
3. **Проверить восстановление до того, как понадобится.** Копия, из которой
   ни разу не восстанавливались, — это предположение, а не копия.

## 3. Vercel — хранилище файлов

**Storage → Create Database → Blob.** Обязательно:

- **Access: Private.** Код обращается к стору с `access: "private"`; на публичном
  сторе это не сработает, а данные о расходах и артефакты проектов незачем
  отдавать по прямой ссылке.
- **Регион Frankfurt (fra1)** — пользователи в Европе.
- **Галочку «Add a read-write token env var» нужно поставить.** Она снята по
  умолчанию, а без неё не появится `BLOB_READ_WRITE_TOKEN`, и приложение уйдёт
  в режим памяти: счётчик расходов обнулится при перезапуске, а жёсткий стоп
  по бюджету перестанет работать.
- Поле префикса оставить пустым, иначе переменные получат другие имена.

Регион функций привести к тому же: **Settings → Functions → Region → fra1**.
Иначе каждое обращение к счётчику ходит через Атлантику, а их на генерацию три.

### Команда сборки и регион

Кликать в панели не нужно: и то, и другое задано в `vercel.ts` в корне
репозитория, поэтому переживает пересоздание проекта и видно в истории
изменений.

```ts
buildCommand: "npx payload migrate && next build",
regions: ["fra1"],
```

Миграции применяются при деплое, а не на лету: `push` включён только вне
продакшена, поэтому схема в проде меняется исключительно миграциями из
репозитория. Автоматическое изменение схемы в бою — способ потерять данные.

Регион `fra1` — потому что там же база и Blob. По умолчанию функции уезжают
в Вашингтон, и каждое обращение к хранилищу идёт через Атлантику.

## 5. Отдельный стенд

**Ветку базы создавать не нужно.** Интеграция Neon в Vercel заводит её сама
на каждый preview-деплой и подставляет строку подключения в это конкретное
развёртывание. Проверить можно в панели Neon: рядом с `main` появляется
ветка вида `preview/имя-ветки`, созданная Vercel.

Одна тонкость, из-за которой в коде отдельный модуль `lib/database-url.ts`:
интеграция подставляет ветку в `DATABASE_URL`, но `POSTGRES_URL` при этом
может остаться от боевой базы. Если брать `POSTGRES_URL` раньше, стенд молча
пишет в продакшен — ничего не падает, и заметно это станет по данным.
Поэтому порядок такой: `DATABASE_URI` → `DATABASE_URL` → `POSTGRES_URL`,
и выбранный узел пишется в лог сборки строкой `[db] подключение из ...`.

**Первым делом после деплоя посмотрите эту строку в логе.** Если на стенде
там боевой узел — значит интеграция ветку не подставила, и дальше ходить
нельзя.

Blob при этом общий для обеих сред. Для артефактов это терпимо: пути
разведены по идентификатору проекта, а проекты на стенде свои. Если понадобится
полная изоляция — заведите второй стор и пропишите его токен только для Preview.

## 6. Resend — письма (нужен с T02)

Вход по одноразовому коду без доставки писем бессмысленен, поэтому шаг
обязательный, хоть и относится к следующей задаче.

1. Завести проект в Resend, добавить домен.
2. Прописать записи **SPF и DKIM** в DNS домена. Без них коды уедут в спам,
   и продукт будет выглядеть сломанным.
3. Ключ в `RESEND_API_KEY`.
4. Отправитель — на своём домене, не на общем поддомене сервиса.

Бесплатного уровня (около 3 000 писем в месяц) хватит надолго: одно письмо
на вход раз в несколько дней на пользователя.

## 7. Первый запуск

После первого деплоя админка Payload на `/admin` предложит создать первого
пользователя. Создайте себе учётную запись и **сразу поставьте роль `admin`** —
у первого пользователя она не проставляется автоматически.

Дальше приглашения выдаются двумя способами, оба приводят к одному результату:

- **Из админки:** коллекция Invitations → Create, достаточно ввести адрес.
  Токен, срок и письмо выпишет хук.
- **Из терминала:** `npm run invite -- someone@example.com "заметка"`.
  Ссылка печатается в вывод, письмо уходит при заданном `RESEND_API_KEY`.

Ссылка одноразовая и живёт две недели. Если приглашённый её потеряет, он
войдёт по коду на тот же адрес — приглашение примется автоматически.

## 8. Локальная разработка

База поднимается в Docker:

```bash
npm run db:up
```

Порт 5434, а не стандартный 5432 — на машине разработки 5433 занят OrbStack,
а 5432 лучше оставить свободным для локального Postgres, если он появится.

```bash
npm run dev
```

Проверки перед коммитом:

```bash
npm run build && npx eslint src --max-warnings=0 && npm run smoke && npm run test
```

Сквозные проверки в браузере:

```bash
npm run test:e2e
```
