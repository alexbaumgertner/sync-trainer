# Работа над релизом

R1, R2 и R3 сделаны и выкачены. Спецификации и журналы решений:
`docs/r1-spec.md`, `docs/r2-spec.md`, `docs/r3-spec.md` и соответствующие
`*-tasks.md`. Журнал решений читать до правки кода: он объясняет, почему
сделано так, и что уже пробовали.

**Одна задача — одна сессия.** Не браться за «сделай R1» целиком: это 5–7 недель
работы, на такой дистанции агент уплывает от спецификации независимо от модели
и инструмента.

Порядок: взять первую задачу `todo` с выполненными зависимостями → прочитать её
критерии приёмки и требования по идентификаторам → сделать → прогнать проверки →
закоммитить → обновить статус и журнал решений в `docs/r1-tasks.md`.

**Ловушка со схемой.** Вне продакшена Payload держит схему через `push`.
Любое изменение, которое он не умеет применить молча, превращается в вопрос
в пустой ввод — и прогон виснет. Три случая, все встречены живьём:

- убрать поле из коллекции (подтверждение на удаление колонок);
- добавить значение в перечисление (`ALTER TYPE ... ADD VALUE`);
- снять `NOT NULL` — то же сокращение схемы, только с другой стороны.

Симптом: много упавших файлов сразу либо `payload migrate`, висящий без
вывода. Лечится применением изменения руками:

```
docker exec sync-trainer-pg psql -U dev -d sync_trainer -c '<ALTER ...>'
```

На проде схему меняет только миграция из репозитория, и вопросов она не
задаёт. Проверять: `docker exec sync-trainer-pg psql -U dev -d sync_trainer
-c '\d glossary_terms'`.

Проверки перед коммитом:

```
npm run build && npx eslint src tests --max-warnings=0 && npm run smoke && npm run test && npm run test:e2e
```

Сквозные проверки в списке не были, и это дорого обошлось: три из них
краснели неделю незамеченными, описывая поведение, которого уже нет. Хуже
того, четвёртая ловила настоящую поломку — пользователя с записями в метриках
нельзя было удалить, — и о ней никто не знал. Они медленные, но собирают
приложение целиком и видят то, чего не видит ни один модульный тест.

**После каждого заслона — выломать его и убедиться, что тест покраснел.**
В R3 это дважды поймало проверки, которые проходили при сломанном коде:
одна зависела от послушания модели, другая смотрела не на то. Тест, который
не падает от поломки, хуже отсутствующего — он даёт ложную уверенность.

Что переиспользуется и не переписывается: `src/lib/ssml.ts` (нарезка под лимит
5000 байт), `src/lib/silence.ts` (MP3-тишина для text-режима),
`src/lib/google-tts.ts` (синтез и склейка), `src/lib/voices.ts`,
`src/lib/budget.ts` (проверка лимита, расширяется третьим условием),
`src/lib/glossary-store.ts` (правило «модель только добавляет» и слои
глоссария — оно одно на все маршруты, копий быть не должно).

Если в работе выясняется, что спецификация неверна — запись в журнал решений
и правка спецификации. Молча отклоняться от неё нельзя.
